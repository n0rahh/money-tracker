# Milestone 4: rulings made during execution

Decisions taken on the owner's behalf while executing the M4 plan with subagents (2026-10-20), in the order they were made. Each line says what was found, what was decided, why, and what it costs if wrong. Rework anything you disagree with. The plan's "Deviations accepted in execution" block points here.

1. ## Rulings (pre-execution)
2. Ruling: the Shortcut signs in with an email/password credential linked to the owner's Google account, not with the SDK's refresh token. Why: a password can be reset from the app and the Email/Password provider turned off in the console, while a refresh token does not expire on its own (spec §5). The rules do not change: they already accept `source: "shortcut"` and know the owner by the token's email and `email_verified` alone. Cost if wrong: the password lives in the Shortcut, in iCloud, so whoever has the Shortcut can sign in as the owner until a Reset.
3. Ruling: the app makes the Shortcut's exact two calls itself. "Send a test entry" writes a real 0.01 entry with Undo, and the page decodes `email_verified` from the token. Why: the one unverified assumption, that a password sign-in keeps the Google-verified flag, is then checked on the owner's phone, with a fallback (Send verification email). Cost if wrong: a stray 0.01 entry when Undo is missed.
4. Ruling: the category dictionary is pasted into the Shortcut once. The Shortcut fetches no categories when it runs on the watch, and the page builds the dictionary again at any time. Why: the watch makes only the two calls, and the rules accept any `categoryId`, so an older copy still writes valid entries. Cost if wrong: a new category is missing from the Shortcut's list until the owner copies the dictionary again.
5. Ruling: the REST create carries no `createdAt` or `updatedAt`. Why: REST cannot set server timestamps, and both fields are optional in the rules and the mapper. Cost if wrong: Shortcut entries have no creation time, which is informational only.
6. Ruling: opus implementers for Task 1 (data layer, REST client, emulator test), Task 2 (the page) and Task 3 (the docs); sonnet reviewers; an opus whole-branch review. Tasks 1 and 3 run in parallel on disjoint files, and Task 2 waits for Task 1. As in M3, every agent has its own scratch directory, reviewers work in worktrees on their own emulator ports, staging is by explicit path, and every commit carries the trailer. Why: Task 1's emulator work had unknowns (the Auth emulator's admin endpoints), and the docs in parallel save a round. Cost if wrong: more reviewer load.
7. Task 3: implementer a7e2b6cb2d5e1f9dc (opus), commit d1edb1a (`docs/shortcut.md`, spec §7, §10, §11, §14 and §15, README, device checklist). Findings, from the Shortcuts string tables that ship with macOS 15: Format Number has only "Decimal Places", with no switch for grouping; Get Contents of URL probably does not stop on a 4xx answer; and the SDK links a password through `accounts:signUp`. Ruling, four recipe amendments (plan amended in 5766587): step 4 is Format Number + Replace Text (`[^0-9]` → nothing); step 13 is one Text holding the whole `{"fields":{…}}` body; step 14 sends it as Request Body "File" with both headers, then an If on the answer's `name` shows "Added …" or `error.message`; and the owner keeps "Enable create (sign-up)" on until the password exists, with its own sentence for `auth/admin-restricted-operation`. Why: Format Number can write 1250 as `1,250` or `1 250`, and Firestore refuses such an amount with 400, so every amount of 10 or more would fail; the raw body avoids the editor for typed JSON keys; without the If a refused write would still say "Added …"; and a blocked sign-up would otherwise show a raw error. Cost if wrong: one action more than needed if Format Number never groups, and a console switch toggled for nothing if sign-ups do not block linking.

9. Ruling (Task 1, concern 1): Remove is dropped. Finding: in the Auth emulator, unlinking the password provider also clears the account's email and `emailVerified`. Google sign-ins and token refreshes then carry no email, the rules refuse everything, and the app signs the owner out. Production cannot be tried locally. Ruling: the page has no Remove, and Reset revokes an old Shortcut, because the old password stops working. Why: one tap must not be able to lock the owner out of the app, and Reset revokes just as well. Cost if wrong: a password, once created, stays on the account; it can be replaced (Reset), or the provider turned off in the console.
10. Ruling (Task 1, concern 2): the claim check after Create and Reset. Finding: nothing local can check the link flow. The Auth emulator refuses a same-email link (`EMAIL_EXISTS`), and its link path sets the account-level `emailVerified` to false. If production did the same, every token of the owner, the Google session's included, would carry `email_verified: false` from its next refresh, and every read in the app would be refused. Ruling: right after a Create or Reset the page reads `email_verified` from a forced token refresh. When it is not true, the page sends Firebase's verification email at once and reads "Your email needs re-verifying for password sign-in. We sent a verification email to <email>: open its link, then come back.", with "Send again"; a send that fails is toasted and never described as sent. Why: this is the answer to the one unproven assumption. The owner learns it on the phone the moment it happens, not an hour later as permission errors. Cost if wrong: one forced token refresh per change.
11. Ruling (Task 1, concern 3): a blocked popup gets a way out. `reauthenticateOwner` is exported, `auth/popup-blocked` has its own sentence (final wording in item 23), and the page's "Confirm with Google" button calls `reauthenticateOwner` from its own tap, then repeats the Create or Reset by itself. Why: the popup that `withRecentLogin` opens after an awaited refusal is likely blocked on iOS. Cost if wrong: a button that rarely shows.
12. Ruling (Task 1, concern 4): a reset may sign out the owner's other devices, because Firebase ends refresh tokens on a password change; the emulator does not model it. The page's Reset note and the docs say so. Cost if wrong: none.
13. Ruling (Task 1, concern 7, and deviations 2 and 4): 15 s timeouts and three more codes. Each REST call gets `AbortSignal.timeout` with 15 s, and a timeout or an abort rejects with `TIMEOUT` (status 0): "The request timed out. Check the connection and try again." `BAD_RESPONSE` stops a 2xx answer without an `idToken` or a `name` (a Wi-Fi login page, say). `PASSWORD_LOGIN_DISABLED` reads as the console sentence. Why: a hung request kept the test button disabled until the browser gave up; a 2xx without a token would have sent `Bearer undefined` and got a puzzling 401; and a password sign-in with the provider off answers `PASSWORD_LOGIN_DISABLED`, not `OPERATION_NOT_ALLOWED`. Cost if wrong: on a very slow network a call fails after 15 s.

Why: the owner pastes a URL instead of typing a key and an id into a template on the phone. Cost if wrong: two more fields on the page.

Ruling (Minors 2 and 3): dictionaries without dots, in order. `categoryDictionary` writes the JSON text line by line, so names of digits only ("2026", "7") keep their place in the categories' order; an object would have moved them to the front. Every "." is dropped from the names: Shortcuts reads a dotted key as a path into the dictionary, as step 14 does with `error.message`, so "Dr. visits" would find no id at step 9. A repeated name, also one that repeats only once its dots are gone, gets " (2)", " (3)" …. Why: the Shortcut's list then follows the app's order (unless Shortcuts sorts "All Keys", a device check), and no category goes missing. Cost if wrong: a category shows without its dots in the Shortcut's list.
20. Ruling (the Task 1 review's note 3 for Task 2, adopted for the fix wave): the proactive re-sign-in. At the start of a Create or Reset tap the page reads the cached token's `authTime`. When the sign-in is older than 4 minutes it signs in again with the Google popup first; `withRecentLogin` stays the safety net, and "Confirm with Google" covers a blocked popup. Why: the owner's session is months old, and Firebase allows a change of sign-in methods only a few minutes after a sign-in. The first Create or Reset would almost always fail with `requires-recent-login`, and the popup opened after that awaited refusal is the one iOS blocks: three taps instead of one. Cost if wrong: if linking needs no recent login, Create costs one extra Google tap after a long session; Reset needs it either way.
21. Ruling (the Task 1 review's note 4 for Task 2, adopted for the fix wave): the test section is gated. Until a password exists, part 3 is disabled and reads "Create the password in step 1 first." Why: with no password the test can only fail, with "Wrong password. Reset it in step 1 and paste the new one.", while step 1 offers Create. Cost if wrong: none.
